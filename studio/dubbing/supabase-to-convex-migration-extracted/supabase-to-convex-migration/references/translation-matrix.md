# Supabase → Convex Translation Matrix

Full mapping table, expanded past schema/RLS/subscriptions/edge-functions to cover the categories that cause mid-migration surprises when they're skipped. Read the note under any row before applying it — several of these look like a clean 1:1 swap and aren't.

| Supabase (Relational) | Convex (Document) | AI Instruction |
|---|---|---|
| Postgres tables + columns | TypeScript schema (`defineTable` + `v` validators) | Map each column's *type* to a validator. This covers shape only — see the constraints row below for everything a validator can't do. |
| `UNIQUE` / `CHECK` / DB-computed `DEFAULT` | No schema-layer equivalent | Reimplement as explicit logic inside the mutation that writes the table — e.g. query an index for an existing match before insert to enforce uniqueness. A `v` validator checks that a field is a string; it has no idea whether that string is already taken. |
| Foreign keys (Postgres UUID) | `v.id("table")` | Import loosely as `v.union(v.string(), v.id("table"))`, re-link via a migration once every referenced document exists, then tighten to `v.id("table")` alone. Never coerce a raw UUID string straight into a strict `v.id()` field on first import — full detail and code in `execution-playbook.md`. |
| Row Level Security policies | Manual authorization checks | Move the identity/role part to an explicit check at the top of **every** query and mutation (not just queries). Move the row-filtering part into the query body itself (`.withIndex`/`.filter`). RLS did both jobs in one policy; Convex needs both done explicitly, and they live in different parts of the function. |
| Realtime subscriptions / manual `useEffect` fetch-on-mount | `useQuery` (reactive) | Delete the manual subscription/fetch code entirely — don't leave it "just in case." Convex re-renders automatically when the underlying documents change. |
| Edge Function that calls an external API | Convex **action** | Move only the external-call portion. If the action also needs to persist something, it calls a mutation to do the actual write (`ctx.runMutation`) — actions aren't transactional the way mutations are. |
| Postgres trigger with no external call (DB-only) | Logic inside the relevant **mutation**, or a scheduled internal mutation | This is *not* an action. Mutations already get atomic, transactional access across tables — that's what the trigger was leaning on Postgres for. Making it an action would lose that transactionality for no benefit. |
| Supabase Auth (GoTrue) | External identity provider (Clerk / Auth0 / WorkOS / Convex Auth) + `ctx.auth.getUserIdentity()` in each function | Not a translation — a provider swap. Existing users, password hashes, and sessions don't carry over automatically. Scope this as its own workstream (see SKILL.md); don't let it hide inside the RLS→auth-check work above. |
| Supabase Storage buckets | Convex file storage (`ctx.storage`) | Files must be re-uploaded into Convex storage, which issues new storage IDs. Anything in the database referencing an old bucket path/URL has the same re-linking problem as a foreign key — treat it the same way. |
| Edge Function / build-time secrets (`.env`) | Convex environment variables | `npx convex env set KEY value` (or the dashboard), set separately for the dev and prod deployments. These do not migrate automatically — an action calling out to Stripe with no key set will fail loudly the first time it runs in the new environment, not at deploy time. |
| `SELECT ... LIMIT/OFFSET` over a large or unindexed table | `.take(n)` or `.paginate()`, filtered with `.withIndex` | Convex enforces a read cap per query/mutation. A `select('*')`-style read that worked fine in Postgres can throw in Convex on a large table if it isn't paginated or narrowed by an index first. |
| Aggregate functions (`COUNT`, `GROUP BY`, window functions) / full-text search (`to_tsvector`) | Hand-written TypeScript over an indexed subset, or a purpose-built Convex component | There's no query-language equivalent to reach for. Either compute it in code over a bounded, indexed set of documents, or use a dedicated component (e.g. a search component) for anything at real scale — don't hand-roll full-text search over `.collect()`. |

## The two rows most often done halfway

**RLS → auth checks.** It's common to add an identity check at the top of a query and stop there, leaving the rest of the query returning every row in the table. That's a completed *authentication* check and an unfinished *authorization* migration — the query still needs to filter which rows come back based on who's asking, exactly like the original policy did.

**Foreign keys → native IDs.** It's common to import the data, get the union type compiling, and call it done — without ever running the migration pass that actually rewrites the loose string references to real `v.id()` values. The schema will happily deploy with `v.union(v.string(), v.id(...))` forever; nothing forces the tightening step to happen unless you do it deliberately. See `execution-playbook.md` for the full sequence, including how to confirm it's actually finished.
